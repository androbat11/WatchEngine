# Debouncer

## What It Is

The Debouncer sits between the Reactor and the Dispatcher.
Its only job is to decide: **should this event be forwarded, or dropped?**

It exists because the OS is too noisy. When you save a file in your editor,
the operating system does not fire one event. It fires many — sometimes 5 to 15
in under 100 milliseconds. If every event reached a plugin, you would get 15
identical notifications for a single save. The Debouncer collapses that burst
into one.

---

## The Concept: Debounce

Imagine a light switch that bounces when you flip it.
In electronics, "debouncing" means: wait until the signal has been stable
for a minimum period before acting on it.

In WatchEngine:

- "Stable" means: no new event for the same file within the time window
- "Time window" means: a configurable duration (default 300ms)

```text
File saved (OS fires 6 events in 80ms)

Timeline:
  0ms   ── event ──► [Debouncer]  FORWARD  ✓  (first time seen)
  10ms  ── event ──► [Debouncer]  DROP     ✗  (within 300ms window)
  25ms  ── event ──► [Debouncer]  DROP     ✗  (within 300ms window)
  40ms  ── event ──► [Debouncer]  DROP     ✗  (within 300ms window)
  60ms  ── event ──► [Debouncer]  DROP     ✗  (within 300ms window)
  80ms  ── event ──► [Debouncer]  DROP     ✗  (within 300ms window)

  Plugin receives: 1 event  (not 6)
```

## How It Works Internally

The Debouncer keeps a memory of the last time it saw each file path.

```text
State: HashMap<PathBuf, Instant>

  {
    "/src/main.ts"    => Instant(t=0ms),
    "/src/config.ts"  => Instant(t=150ms),
  }
```

When an event arrives for `/src/main.ts` at `t=50ms`:

1. Look up `/src/main.ts` in the map → found, last seen at `t=0ms`
2. Calculate elapsed: `50ms - 0ms = 50ms`
3. Compare to window: `50ms < 300ms` → **DROP**, update timestamp to `t=50ms`

When an event arrives for `/src/main.ts` at `t=400ms`:

1. Look up `/src/main.ts` → found, last seen at `t=50ms`
2. Calculate elapsed: `400ms - 50ms = 350ms`
3. Compare to window: `350ms > 300ms` → **FORWARD**, update timestamp to `t=400ms`

## Its Place in the Kernel

```text
Reactor
  │
  │  FileEvent (raw, can be many per second)
  ▼
Debouncer  ◄── you are here
  │
  │  FileEvent (settled, at most one per path per window)
  ▼
Dispatcher
```

The Debouncer never modifies the event. It either forwards the original
`FileEvent` unchanged or silently drops it. The Dispatcher never knows
how many events were dropped.

## Rust Concepts Involved

**`HashMap<K, V>`**
A hash map stores key-value pairs with O(1) lookup.
Here: key = file path, value = last time that path was seen.
Reading: The Rust Book, Chapter 8.3 — Hash Maps.

**`std::time::Instant`**
An `Instant` captures a point in time. It cannot be printed as a clock time,
but you can measure elapsed time from it with `.elapsed()`.
It is monotonic — it never goes backwards (unlike wall clock time).

**`std::time::Duration`**
A `Duration` represents a span of time.
`Duration::from_millis(300)` creates a 300ms duration.
You compare: `if instant.elapsed() > self.window`.

---

## Pseudocode

```text
struct Debouncer {
    last_seen: HashMap<PathBuf, Instant>,
    window:    Duration,
}

fn should_forward(event) -> bool {
    match last_seen.get(event.path) {
        None => {
            last_seen.insert(event.path, Instant::now())
            return true
        }
        Some(last) => {
            last_seen.insert(event.path, Instant::now())  // always update
            return last.elapsed() >= window
        }
    }
}
```

## Recommended Reading

### The Concept and Its Origins

**Debounce vs Throttle — visual explainer**
Before reading anything else, watch or read a visual comparison of debounce
and throttle. They solve the same "too many events" problem differently.
Debounce: fires after quiet period. Throttle: fires at a fixed rate.
WatchEngine uses debounce because you want to react after the user stops
saving, not at a fixed interval.
Search: "debounce vs throttle css-tricks" — CSS-Tricks has the best visual.

**Hardware origins of debouncing**
The term comes from electrical engineering — mechanical switches physically
"bounce" when pressed, causing multiple electrical signals. The software
pattern is a direct metaphor. Understanding the hardware origin makes the
concept intuitive.
Search: "switch debouncing electronics explained"

**Event coalescing in operating systems**
The OS itself coalesces some events before delivering them (FSEvents does this
explicitly — see the architecture doc). The Debouncer does a second layer of
coalescing at the application level. Understanding why both layers exist is
important for reasoning about event loss and correctness.
Search: "FSEvents coalescing macOS" or read the FSEvents developer docs.

### The Pattern Behind the Debouncer

**Proxy Pattern (Gang of Four)**
The Debouncer is a Protection Proxy — it sits in front of the Dispatcher and
controls access to it. The Dispatcher does not know the Debouncer exists; it
just receives events. This is the Proxy pattern: same interface, added behavior.
Read: GoF "Design Patterns" — Proxy chapter.
Search: "Proxy pattern explained smart proxy"

**Idempotency and event deduplication**
The Debouncer's goal is related to idempotency — making repeated identical
operations have the same effect as one. Event deduplication is a core concept
in distributed systems and message queues (Kafka, SQS). The Debouncer is a
simple local version of the same idea.
Search: "idempotency event deduplication message queues"

### HashMap Internals

**How HashMap works — hashing and collision resolution**
Rust's `HashMap` uses the SipHash algorithm by default (switched to a faster
variant called AHash in recent Rust versions). Understanding the basics of
hashing and why O(1) lookup holds on average (not worst case) gives you
confidence in using it as the Debouncer's state.
Search: "how hashmap works internally" — any data structures resource.

**`std::collections::HashMap` — Rust stdlib**
The full API reference. Pay attention to the `.entry()` API — it is the
idiomatic way to insert-or-update a key in one step, which is exactly what
`should_forward()` needs.
<https://doc.rust-lang.org/std/collections/struct.HashMap.html>

**`std::time::Instant` — monotonic clocks**
`Instant` uses the OS monotonic clock, not the wall clock. Understanding the
difference (wall clock can go backwards during NTP sync; monotonic never does)
explains why `Instant` is the correct type for measuring elapsed time.
<https://doc.rust-lang.org/std/time/struct.Instant.html>

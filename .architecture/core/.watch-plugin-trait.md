# WatchPlugin Trait

## What It Is

The `WatchPlugin` trait is the microkernel boundary.
It is the contract every plugin must fulfill to work with the kernel.
The kernel knows nothing about any concrete plugin — it only knows this trait.

```rust
pub trait WatchPlugin: Send + Sync {
    fn id(&self) -> &str;
    fn extensions(&self) -> &[&str];
    fn setup(&mut self, config: &Config) -> Result<Vec<PathBuf>, WatchError>;
    fn on_event(&self, event: &FileEvent);
}
```

This is the only surface the kernel touches. If a type implements these four
methods, the kernel can use it as a plugin — whether it is a TypeScript watcher,
a JavaScript watcher, or something that does not exist yet.

---

## Each Method Explained

### `fn id(&self) -> &str`

Returns a unique identifier for the plugin (e.g. `"typescript"`).
Used for logging and debugging. The kernel identifies plugins by their id
when printing which plugin handled an event.

### `fn extensions(&self) -> &[&str]`

Returns the file extensions this plugin cares about.
Examples: `&[".ts", ".tsx"]` for TypeScript, `&["*"]` for Generic.

The `"*"` wildcard means "match everything." The Plugin Registry checks for
this sentinel value during `find_by_extension` to implement the fallback.

### `fn setup(&mut self, config: &Config) -> Result<Vec<PathBuf>, WatchError>`

Called once at startup by the Plugin Registry.
Returns the list of directories the plugin wants the kernel to watch.

This is the plugin's only opportunity to interact with the file system before
the event loop starts. A TypeScript plugin walks the directory tree here and
returns every folder that contains `.ts` files. The kernel then registers those
folders with the OS watcher.

`&mut self` means the plugin can store state during setup (e.g. cache the
discovered paths for later use in `on_event`).

### `fn on_event(&self, event: &FileEvent)`

Called by the Dispatcher every time a matching file changes.

`&self` (not `&mut self`) means the plugin cannot modify its own configuration
while handling events. This is intentional: event handling is read-only.
The plugin reads the event and emits output. That is all.

---

## Why `Send + Sync`

These are marker traits that Rust uses to reason about thread safety.

**`Send`** — the plugin can be moved to another thread.
The CLI creates plugins on the main thread. The Dispatcher calls them from the
event loop thread. Without `Send`, Rust would reject this at compile time.

**`Sync`** — the plugin can be referenced from multiple threads simultaneously.
If the Dispatcher ever calls two plugins concurrently, each holds a reference
to the registry. Without `Sync`, this would be rejected.

Rust enforces both at compile time. You cannot accidentally have a thread-safety
bug here — the trait bound prevents it before the code runs.

## The Lifecycle

```text
Startup
  │
  ├── CLI creates plugin instances
  ├── Registry.register(Box::new(TypeScriptPlugin::new()))
  ├── Registry.setup_all(&config)
  │     └── plugin.setup(&config) → returns Vec<PathBuf>
  │
Runtime (event loop running)
  │
  ├── Dispatcher.dispatch(&event)
  │     └── plugin.on_event(&event)  ← called repeatedly
  │
Shutdown
  │
  └── Registry.teardown_all()
        └── plugin dropped (Rust's Drop trait handles cleanup)
```

`setup()` runs once. `on_event()` runs many times.
The plugin must be ready to handle `on_event` immediately after `setup` returns.

---

## How the Kernel Stays Decoupled

The kernel crate (`watch-engine-core`) defines the trait.
The plugin implementations (`TypeScriptPlugin`, etc.) live in `watch-engine` (the binary crate).
The kernel never imports any concrete plugin.

```text
watch-engine-core defines:   WatchPlugin trait
watch-engine implements:     TypeScriptPlugin, JavaScriptPlugin, GenericPlugin
watch-engine-core never sees: TypeScriptPlugin
```

This means you can add a new plugin by writing one new struct in the binary
crate and registering it in `main.rs`. The kernel crate never changes.

## Rust Concepts Involved

**Traits as interfaces**
A Rust trait is similar to an interface in Java or a protocol in Swift.
It defines what methods a type must provide, not how they are implemented.
Read: The Rust Book, Chapter 10.2 — <https://doc.rust-lang.org/book/ch10-02-traits.html>

**`&self` vs `&mut self` in trait methods**
`&self` borrows the value immutably — the method can read but not write.
`&mut self` borrows mutably — the method can read and write.
Choosing correctly is part of the contract: `setup` needs mutation, `on_event` does not.
Read: The Rust Book, Chapter 4.2 — <https://doc.rust-lang.org/book/ch04-02-references-and-borrowing.html>

**Marker traits: `Send` and `Sync`**
`Send` and `Sync` are auto-implemented by the compiler for most types.
They are violated by types like `Rc<T>` (not `Send`) or `Cell<T>` (not `Sync`).
If a plugin accidentally uses `Rc` internally, the compiler will refuse to let
you register it — the `Send + Sync` bound catches the bug at compile time.
Read: The Rustonomicon, Chapter 8 — <https://doc.rust-lang.org/nomicon/send-and-sync.html>

**`Box<dyn WatchPlugin>`**
The kernel stores plugins as `Box<dyn WatchPlugin>`. This is dynamic dispatch —
the concrete type is erased, only the trait interface remains. The `Box` is
needed because trait objects have no known size at compile time.
Read: The Rust Book, Chapter 17.2 — <https://doc.rust-lang.org/book/ch17-02-trait-objects.html>

## Recommended Reading

### The Pattern Behind This Trait

**Microkernel Architecture — plugin contracts**
The `WatchPlugin` trait is the formal definition of what a plugin is in the
microkernel model. Reading about microkernel architecture in operating systems
(Mach, L4, QNX) gives context for why the contract is minimal by design.
Search: "microkernel architecture plugin contract" or "QNX microkernel design"

**Interface Segregation Principle (SOLID)**
The trait has exactly four methods — no more. ISP says a client should not
be forced to depend on methods it does not use. Every method in `WatchPlugin`
is used by the kernel. If we added a method only some plugins needed,
we would be violating ISP.
Search: "Interface Segregation Principle SOLID explained"

**Liskov Substitution Principle (SOLID)**
Any plugin that implements `WatchPlugin` must be substitutable for any other.
The kernel must work correctly regardless of which concrete plugin it receives.
This is LSP — and it is what the trait guarantees.
Search: "Liskov Substitution Principle explained"

**Open/Closed Principle (SOLID)**
The kernel is open for extension (new plugins) but closed for modification
(you don't change the kernel to add a plugin). The `WatchPlugin` trait is the
mechanism that makes this possible.
Search: "Open Closed Principle SOLID"

**Plugin systems in practice — real examples**
VS Code, Vim, and Webpack all define a plugin contract similar to this trait.
Reading one real plugin API's design philosophy gives you practical intuition.
Search: "VS Code extension API activation events" or "webpack plugin API tap"

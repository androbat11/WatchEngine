# Reactor

## What It Is

The Reactor is the heart of the kernel. It is the event loop — the thing that
runs forever, waiting for file events, and pushing them forward into the rest
of the system.

It owns the receiving end of a channel that the OS adapter writes into.
Everything starts here. Nothing happens in WatchEngine until the Reactor
receives an event.

---

## The Reactor Pattern

The "Reactor" name comes from a well-known systems design pattern.
The idea: instead of asking "did something change?" on a timer (polling),
you register interest and **react** when the OS tells you something changed.

```text
POLLING (bad)                      REACTOR PATTERN (good)
─────────────────────              ─────────────────────────────────
loop every 100ms:                  OS: "main.ts changed"
  did main.ts change?  → no            │
  did main.ts change?  → no            ▼
  did main.ts change?  → no       Reactor wakes up
  did main.ts change?  → yes!     Reactor processes event
  handle it                       Reactor goes back to sleep
```

Polling wastes CPU constantly checking. The Reactor uses zero CPU while idle
because it is blocked on `recv()` — a call that sleeps the thread until
a message arrives.

## Its Place in the Kernel

```text
notify Adapter (outside kernel)
  │
  │  Sender<FileEvent>  ──────────────────────┐
  │                                            │
  │                                            ▼
  │                                   Reactor  ◄── you are here
  │                                     │
  │                                     │  FileEvent
  │                                     ▼
  │                                   Debouncer
  │                                     │
  │                                     ▼
  │                                   Dispatcher
  │                                     │
  │                                     ▼
  │                                   Plugins
```

The Reactor is the first kernel component to touch every event.
It normalizes the raw event and hands it to the Debouncer.

---

## The Channel: How Events Flow In

The Reactor uses a **channel** — a Rust standard library mechanism for
passing data between threads safely.

A channel has two ends:
- `Sender<FileEvent>` — the writing end. The notify adapter holds this.
- `Receiver<FileEvent>` — the reading end. The Reactor holds this.

```text
notify Adapter                    Reactor
──────────────                    ───────
OS fires event
translate to FileEvent
tx.send(event) ──────────────►  rx.recv()  ← blocks here until event arrives
                                  returns Ok(event)
                                  process it
                                rx.recv()  ← blocks again
```

When the Sender is dropped (process exits), `rx.recv()` returns `Err()`
and the Reactor loop exits cleanly. This is the shutdown mechanism.

---

## The Event Loop

```text
fn run():
  loop:
    match receiver.recv():
      Ok(event)  →  pass to Debouncer
                    if Debouncer says forward:
                        pass to Dispatcher
      Err(_)     →  break  (channel closed, shutdown)
```

This loop runs for the entire lifetime of the process.
It is the "always running" part of the kernel.

---

## Normalization

The Reactor translates the raw OS event (from the notify adapter) into
the kernel's internal `FileEvent` type before doing anything else.

This happens at the channel boundary — the notify adapter sends a `FileEvent`
(already translated from `notify::Event`), and the Reactor receives it ready
to use. The Reactor itself does minimal normalization: mainly filtering out
events for paths it does not recognize (e.g., temporary editor files like
`.main.ts.swp`).

## Rust Concepts Involved

**`std::sync::mpsc`**
`mpsc` stands for multi-producer, single-consumer.
Multiple senders can write to the same channel. Only one receiver reads from it.
In WatchEngine: one sender (notify adapter), one receiver (Reactor).
`mpsc::channel()` returns a `(Sender<T>, Receiver<T>)` tuple.
Reading: The Rust Book, Chapter 16.2 — Using Message Passing to Transfer Data Between Threads.

**Blocking vs non-blocking receive**
`receiver.recv()` blocks the current thread until a message arrives.
This is efficient — the OS scheduler puts the thread to sleep and wakes it
only when data is available. Zero CPU used while waiting.
The alternative `receiver.try_recv()` returns immediately with `Err` if no
message is available — useful for polling, but wrong here.

**`loop` and `match` together**
The event loop is a `loop {}` (infinite loop) with a `match` on `recv()`.
The `Err(_)` arm is the only exit — it fires when the sender is dropped.
This is idiomatic Rust for "run until shutdown."

**Ownership of the Receiver**
The Reactor owns the `Receiver<FileEvent>`. Nobody else can read from it.
This is enforced by Rust's ownership system at compile time —
you cannot accidentally have two places reading from the same channel.

---

## Pseudocode

```text
struct Reactor {
    receiver: Receiver<FileEvent>,
}

fn run(debouncer, dispatcher):
    loop:
        match self.receiver.recv():
            Ok(event) =>
                if debouncer.should_forward(&event):
                    dispatcher.dispatch(&event)
            Err(_) =>
                break  // sender dropped, exit cleanly
```

## Recommended Reading

### The Pattern Behind the Reactor

**Reactor Pattern — Doug Schmidt's original paper**
The Reactor pattern was formally described by Doug Schmidt in 1995.
It defines an event demultiplexer that waits for events on a set of handles
and dispatches them to the appropriate handlers. WatchEngine's Reactor is a
direct implementation of this pattern, with the OS watcher as the event source.
Search: "Schmidt Reactor pattern 1995" or "reactor pattern event-driven demultiplexer"
Free PDF: search "An Object Behavioral Pattern for Demultiplexing and Dispatching Handles for Synchronous Events"

**Reactor vs Proactor — two models of async I/O**
The Reactor pattern is synchronous notification ("something is ready, go read it").
The Proactor pattern is completion notification ("the read already happened, here is the data").
`inotify` and `FSEvents` are Reactor-style. Windows IOCP is Proactor-style.
Understanding this distinction explains why the notify adapter behaves
differently per OS under the hood.
Search: "Reactor vs Proactor pattern async I/O"

**Event-Driven Architecture — general concept**
The entire WatchEngine system is event-driven: nothing runs until an event
arrives. This article from Martin Fowler explains what EDA means, its benefits
(decoupling, idle efficiency), and its tradeoffs (harder to trace causality).
Search: "Martin Fowler Event-Driven Architecture"
<https://martinfowler.com/articles/201701-event-driven.html>

### Channel Internals

**`std::sync::mpsc` — how Rust channels work internally**
Rust's mpsc channel uses a lock-free queue for the fast path (single sender)
and falls back to a mutex-based queue for multiple senders. Understanding this
explains why `Receiver` is not `Clone` (single consumer by design) and why
`Sender` is `Clone` (multiple producers allowed).
<https://doc.rust-lang.org/std/sync/mpsc/index.html>

**CSP — Communicating Sequential Processes (Tony Hoare)**
Rust channels are inspired by CSP, a formal model for concurrent systems where
processes communicate exclusively by passing messages, never sharing memory.
This is the theoretical foundation behind "do not communicate by sharing memory;
instead, share memory by communicating" — the Go and Rust channel philosophy.
Search: "CSP communicating sequential processes Hoare" or read the Go blog:
<https://go.dev/blog/coop>

**Lock-free data structures and the ABA problem**
The fast path of mpsc uses a lock-free queue. Understanding what "lock-free"
means (progress guarantee, not absence of blocking) and the ABA problem
gives you a much deeper understanding of why channels are designed the way
they are.
Search: "lock-free data structures ABA problem"

### Operating System Scheduler Interaction

**How blocking syscalls work — `epoll`, `kqueue`, `IOCP`**
When the Reactor calls `recv()` and blocks, the OS puts the thread to sleep
via a blocking syscall. On Linux this is `epoll_wait`, on macOS `kqueue`,
on Windows `GetQueuedCompletionStatus`. The notify crate uses these internally.
Understanding the OS side explains why the Reactor uses zero CPU while idle.
Search: "epoll explained Linux" or "kqueue macOS event notification"

# Dispatcher

## What It Is

The Dispatcher is the kernel's decision-maker and caller.
It receives a settled `FileEvent` from the Debouncer and answers one question:
**who needs to know about this, and how do I tell them?**

It does two things:

1. Asks the Plugin Registry: which plugins handle this file extension?
2. Calls `on_event()` on each matching plugin

Optionally, if `--exec` was passed on the CLI, it also runs the user's command.

---

## Its Role in the Kernel

```text
Debouncer
  │
  │  settled FileEvent
  ▼
Dispatcher  ◄── you are here
  │
  ├──► plugin_a.on_event(&event)
  ├──► plugin_b.on_event(&event)
  └──► run --exec command (if configured)
```

The Dispatcher does not know what the plugins do.
It only knows the trait: `plugin.on_event(&event)`.
What happens inside that call is none of the Dispatcher's business.

---

## How It Routes Events

Every `FileEvent` has a `path` field. The Dispatcher extracts the file extension
from that path and uses it to query the Plugin Registry.

```text
event.path = "/project/src/main.ts"
extension  = ".ts"

Registry lookup(".ts") returns:
  - TypeScriptPlugin  (registered for [".ts", ".tsx"])
  - GenericPlugin     (registered for ["*"])

Dispatcher calls:
  TypeScriptPlugin.on_event(&event)
  GenericPlugin.on_event(&event)
```

The `"*"` extension is a wildcard — the GenericPlugin always matches.
A plugin registered for `".rs"` would not be called for a `.ts` event.

---

## The --exec Feature

If the user ran `watch-engine --exec "echo changed"`, the Dispatcher
holds that command string. After calling all plugins, it runs the command:

```text
std::process::Command::new("sh")
    .arg("-c")
    .arg("echo changed")
    .spawn()
```

`.spawn()` is non-blocking — it starts the process and immediately returns.
The Reactor loop continues without waiting for the command to finish.
This is intentional: a slow `--exec` command must not stall the watcher.

## Rust Concepts Involved

**Method calls on trait objects**
`plugin.on_event(&event)` works even though the Dispatcher does not know the
concrete type of `plugin`. This is dynamic dispatch — Rust resolves which
`on_event` implementation to call at runtime via a vtable.
Reading: The Rust Book, Chapter 17.2 — Using Trait Objects.

**`Option<String>` for optional config**
`exec: Option<String>` means the field either holds a command (`Some(cmd)`)
or nothing (`None`). You handle it with `if let Some(cmd) = &self.exec`.
Reading: The Rust Book, Chapter 6.2 — The `match` control flow operator.

**`std::process::Command`**
The standard library's way to run a child process.
`.spawn()` starts it without waiting (non-blocking).
`.output()` starts it and waits for it to finish (blocking) — do NOT use this
in the Dispatcher, it would freeze the event loop.
Reading: <https://doc.rust-lang.org/std/process/struct.Command.html>

### Path extension extraction

```rust
event.path.extension()          // returns Option<&OsStr>
    .and_then(|e| e.to_str())   // converts to Option<&str>
    .unwrap_or("")               // fallback to empty string
```

## Pseudocode

```text
struct Dispatcher {
    registry: PluginRegistry,
    exec:     Option<String>,
}

fn dispatch(event: &FileEvent) {
    let ext = extract_extension(event.path)

    for plugin in registry.find_by_extension(ext) {
        plugin.on_event(event)
    }

    if let Some(cmd) = exec {
        Command::new("sh").arg("-c").arg(cmd).spawn()
    }
}
```

## Recommended Reading

### The Pattern Behind the Dispatcher

**Command Pattern (Gang of Four)**
The Dispatcher implements a variation of the Command pattern. Each call to
`plugin.on_event(&event)` is an encapsulated command — the Dispatcher does
not know what the command does, only how to invoke it. This decoupling is
precisely what makes it possible to add plugins without changing the Dispatcher.
Read: GoF "Design Patterns" — Command chapter.
Or search: "Command pattern explained with examples"

**Message Routing Patterns — Enterprise Integration Patterns**
Gregor Hohpe's "Enterprise Integration Patterns" book defines the concept of
a Message Router — a component that routes a message to the correct handler
based on its content (here: the file extension). The Dispatcher is a
content-based router in EIP terms.
Search: "Enterprise Integration Patterns content-based router Hohpe"
Free reference: <https://www.enterpriseintegrationpatterns.com/patterns/messaging/ContentBasedRouter.html>

**Observer Pattern vs Command Pattern — the difference**
The Dispatcher looks similar to Observer (notify all subscribers), but it is
subtly different: Observer broadcasts to all, Command routes selectively.
Understanding this distinction clarifies why `find_by_extension` exists at all.
Search: "Observer pattern vs Command pattern difference"

### How the Kernel Stays Decoupled

**Dependency Inversion Principle (SOLID)**
The Dispatcher depends on the `WatchPlugin` abstraction (the trait), not on
any concrete plugin. This is the D in SOLID. Understanding DIP explains why
the Dispatcher never imports `TypeScriptPlugin` directly.
Search: "Dependency Inversion Principle explained" — Uncle Bob's articles are good.

**Tell, Don't Ask — OO design principle**
The Dispatcher tells plugins what happened (`on_event`). It does not ask them
for their state and then decide what to do. This principle keeps the Dispatcher
simple and plugins self-contained.
Search: "Tell Don't Ask principle Fowler"

### Process Spawning Internals

**`std::process::Command` — Rust stdlib**
The definitive reference for how Rust spawns child processes, including the
difference between `.spawn()`, `.output()`, and `.status()`.
<https://doc.rust-lang.org/std/process/struct.Command.html>

**How Unix process spawning works (fork + exec)**
On Linux/macOS, `.spawn()` ultimately calls `fork()` then `execve()`.
Understanding fork/exec explains why spawned processes are independent and
why a slow `--exec` command does not block the parent (Reactor loop).
Search: "Unix fork exec explained" — any systems programming resource.

# Domain Types

## What They Are

Domain types are the shared vocabulary of the kernel.
Every component — Reactor, Debouncer, Dispatcher, Registry, and all plugins —
speaks in these types. They live in `watch-engine-core` with zero external
dependencies (except `thiserror` for `WatchError`).

If you change a domain type, every component is affected.
That is why they are defined once, centrally, in the kernel.

---

## `FileEventKind`

Represents what happened to a file. Four possible variants:

```rust
pub enum FileEventKind {
    Created,
    Modified,
    Deleted,
    Renamed { from: PathBuf },
}
```

`Renamed` carries data — the old path. The other three variants carry no data.
This is what makes Rust enums powerful: a variant can be a plain tag or
a tag with attached data. In most languages you need a separate field for this.

The `from` field in `Renamed` is how the Reactor pairs the two OS-level events
(`RENAMED_OLD_NAME` + `RENAMED_NEW_NAME` on Windows, `IN_MOVED_FROM` +
`IN_MOVED_TO` on Linux) into a single semantic event.

---

## `FileEvent`

The normalized event that flows through the entire kernel.

```rust
pub struct FileEvent {
    pub path:      PathBuf,
    pub kind:      FileEventKind,
    pub timestamp: std::time::Instant,
}
```

- `path` — the absolute path to the file that changed
- `kind` — what happened (one of the four variants above)
- `timestamp` — when the Reactor received the event (used by the Debouncer)

`FileEvent` is created exactly once — by the notify adapter when it receives
a raw OS event. After that it is passed by reference (`&FileEvent`) through
every component. Nobody makes a copy of the event.

## `Config`

Built once by the CLI at startup. Handed to the kernel. Never mutated again.

```rust
pub struct Config {
    pub root:        PathBuf,
    pub debounce_ms: u64,
    pub exec:        Option<String>,
}
```

- `root` — the directory being watched (e.g. `/project`)
- `debounce_ms` — the debounce window in milliseconds (default 300)
- `exec` — an optional shell command to run after each settled event

`Option<String>` means the field is either `Some("echo changed")` or `None`.
There is no null in Rust. `Option` is how Rust represents "this might not exist."

## `WatchError`

The kernel's error type. Defined with `thiserror` to reduce boilerplate.

```rust
#[derive(Debug, thiserror::Error)]
pub enum WatchError {
    #[error("IO error: {0}")]
    Io(#[from] std::io::Error),

    #[error("Watcher error: {0}")]
    Watcher(String),

    #[error("Plugin setup failed: {0}")]
    PluginSetup(String),
}
```

`#[from]` on the `Io` variant means: if you have a `std::io::Error`, Rust
will automatically convert it into a `WatchError::Io` using the `?` operator.
This is how idiomatic Rust error propagation works — no `unwrap`, no `panic`.

## Why These Live in the Kernel and Nowhere Else

Every crate in the workspace needs to talk about file events, configuration,
and errors. If each crate defined its own version, you would need conversion
code everywhere. Having one canonical definition in `watch-engine-core` means:

- The Reactor produces a `FileEvent`
- The Debouncer receives a `FileEvent`
- The Dispatcher receives a `FileEvent`
- A plugin's `on_event` receives a `&FileEvent`

Everyone uses the same type. No translation needed.

## Rust Concepts Involved

**Enums with data**
Rust enums are sum types — a value is exactly one of the variants,
and each variant can carry different data. This is more expressive than
C-style enums and more correct than using a struct with optional fields.
Read: The Rust Book, Chapter 6 — <https://doc.rust-lang.org/book/ch06-00-enums.html>

**`PathBuf` vs `Path`**
`PathBuf` is an owned, heap-allocated path (like `String`).
`Path` is a borrowed slice of a path (like `&str`).
Use `PathBuf` when you own and store the path. Use `&Path` when you just read it.
Read: <https://doc.rust-lang.org/std/path/struct.PathBuf.html>

**`Option<T>`**
Rust's way of expressing "a value that might not exist."
Replaces null from other languages. The compiler forces you to handle both cases.
Read: The Rust Book, Chapter 6.1 — <https://doc.rust-lang.org/book/ch06-01-defining-an-enum.html>

**`thiserror` crate**
A derive macro that generates `std::error::Error` implementations.
The `#[error("...")]` attribute defines the human-readable message.
The `#[from]` attribute generates automatic conversions from other error types.
Read: <https://docs.rs/thiserror/latest/thiserror/>

## Recommended Reading

### Type Design Principles

**Making Illegal States Unrepresentable — Yaron Minsky**
The `FileEventKind` enum is an example of this principle in action.
A struct with a `kind: String` field and an optional `old_path: Option<PathBuf>`
could represent impossible states (kind = "Created" but old_path = Some(...)).
The enum makes that impossible at the type level.
Search: "making illegal states unrepresentable" — Minsky's original post or
the many Rust adaptations of the idea.

**Parse, Don't Validate**
Related principle: instead of validating data and then using it, parse it
into a type that is always valid. `FileEventKind::Renamed { from }` is already
parsed — you never have to check "is from populated?".
Search: "parse don't validate Alexis King"

**Algebraic Data Types**
Rust enums are algebraic data types (ADTs) — specifically sum types.
`FileEventKind` is a sum type: a value is Created OR Modified OR Deleted OR Renamed.
`FileEvent` is a product type: a value has a path AND a kind AND a timestamp.
Understanding ADTs gives you the vocabulary to reason about data modeling.
Search: "algebraic data types sum product types explained"

**Domain-Driven Design — Eric Evans**
Placing shared types in a central "kernel" crate is an application of DDD's
concept of a Shared Kernel — a small subset of the domain model that multiple
bounded contexts agree on. The domain types here are that Shared Kernel.
Search: "Domain-Driven Design Shared Kernel pattern"

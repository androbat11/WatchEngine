# WatchEngine — Component Registry

Architecture: **Microkernel**
Language: **Rust**

> **Purpose:** A lightweight, CPU and memory-efficient file watcher.
> WatchEngine is the alternative to heavy language-bundled watchers (e.g. `tsc --watch`).
> It watches files. It does not compile, lint, or run language tooling by default.

---

## 1. Kernel (Always Running)

These components exist regardless of which plugins are loaded.
The kernel compiles and runs with zero plugins present.

### 1.1 Reactor

- Owns the `notify::RecommendedWatcher` instance
- Runs the main event loop (blocking `recv()` on the notify channel)
- Normalizes raw `notify::Event` into internal `FileEvent`
- Pushes `FileEvent` into the Debounce Proxy
- Never blocks on plugin execution
- **Crate:** `notify`

### 1.2 Plugin Registry

- Holds `Vec<Box<dyn WatchPlugin>>` — the catalogue of loaded plugins
- Answers: "which plugins handle this file extension?"
- Calls `plugin.setup(&config)` once per plugin at startup
- Calls `plugin.teardown()` on clean exit
- Instantiates plugins via the CLI flags passed at startup

### 1.3 Debounce Proxy

- Sits between Reactor and Dispatcher
- Coalesces rapid events on the same path within a configurable time window (default: 300ms)
- Only forwards one settled `FileEvent` per path per window
- Prevents CPU spikes during rapid saves (e.g. editor auto-save storms)
- **Crate:** `notify-debouncer-full` or custom via `tokio::time`

### 1.4 Dispatcher

- Receives settled `FileEvent` from the Debounce Proxy
- Queries the Plugin Registry for plugins matching the file extension
- Calls `plugin.on_event(&event)` on each matching plugin
- Spawns each plugin call as an independent `tokio` task (non-blocking)
- If `--exec <cmd>` is provided, runs the user-supplied shell command after plugin dispatch
- `--exec` is a single shared feature in the kernel — not duplicated per plugin

## 2. Core Domain Types

Shared types owned by the kernel. No external crate dependencies.

### 2.1 `FileEvent`

```
path: PathBuf
kind: FileEventKind
timestamp: Instant
```

### 2.2 `FileEventKind`

```
Created
Modified
Deleted
Renamed { from: PathBuf }
```

### 2.3 `Config`

```
root: PathBuf          — directory being watched
debounce_ms: u64       — debounce window in milliseconds
plugins: Vec<String>   — plugin ids enabled at startup
```

### 2.4 `WatchPlugin` Trait (The Kernel Contract)

```rust
pub trait WatchPlugin: Send + Sync {
    fn id(&self) -> &str;
    fn extensions(&self) -> &[&str];
    fn setup(&mut self, config: &Config) -> Result<()>;
    fn on_event(&self, event: &FileEvent);
}
```

This trait IS the microkernel boundary. The kernel only ever sees `Box<dyn WatchPlugin>`.

### 2.5 `WatchError`

Structured error enum for the kernel. Defined with `thiserror`.

## 3. Infrastructure (Outside the Kernel)

Not plugins, not kernel — these feed and drive the kernel.

### 3.1 CLI (`main.rs` + `clap`)

- Entry point of the binary
- Parses user flags: `--typescript`, `--javascript`, `--watch <path>`, `--debounce <ms>`, `--exec <cmd>`
- Builds `Config` from parsed args
- Instantiates and registers plugins into the Plugin Registry
- Hands control to the kernel
- **Crate:** `clap` (derive feature)

### 3.2 OS Adapter (`notify`)

- Feeds raw file system events into the Reactor
- Wraps `FSEvents` (macOS), `inotify` (Linux), `ReadDirectoryChangesW` (Windows)
- The Reactor is the only component that touches this directly
- **Crate:** `notify`

### 3.3 Logger

- Structured logging across all components
- Used by kernel and plugins alike
- **Crate:** `tracing` + `tracing-subscriber`

## 4. Plugins (Microkernel Extensions)

Each plugin implements `WatchPlugin`. The kernel knows none of them by name.

### 4.1 `TypeScriptPlugin`

- **Flag:** `--typescript`
- **Extensions:** `.ts`, `.tsx`
- **`setup()`:** Walks directory tree from `config.root`, finds every directory containing at least one `.ts`/`.tsx` file, registers those directories with the Reactor watcher. No compiler is started.
- **`on_event()`:** Emits the `FileEvent` to stdout. Does NOT invoke `tsc` or any language tooling.
- **Crates:** `walkdir`

### 4.2 `JavaScriptPlugin`

- **Flag:** `--javascript`
- **Extensions:** `.js`, `.mjs`, `.cjs`
- **`setup()`:** Same directory auto-discovery as TypeScript plugin for `.js`/`.mjs`/`.cjs` files.
- **`on_event()`:** Emits the `FileEvent` to stdout. Does NOT invoke `node` or any runtime.
- **Crates:** `walkdir`

### 4.3 `GenericPlugin`

- **Flag:** always loaded as fallback (or `--generic`)
- **Extensions:** `*` (matches everything not claimed by a specific plugin)
- **`setup()`:** Registers the root directory recursively. No file-type filtering.
- **`on_event()`:** Emits the `FileEvent` to stdout.
- **Crates:** none beyond std

## 6. What Still Needs Research

| Topic | Why it matters |
|-------|---------------|
| `notify` event kinds and mapping | Ensure `notify::EventKind` maps cleanly to `FileEventKind` |
| `clap` derive macros | How plugin flags and `--exec` are declared and parsed |
| `tokio::process::Command` | How the Dispatcher runs `--exec` commands without blocking the event loop |
| `Box<dyn Trait> + Send + Sync` | The mechanism that makes the plugin registry work |
| `Arc<RwLock<T>>` | If the Registry needs to be shared across threads |
| `notify-debouncer-full` vs custom debounce | Whether the crate covers the use case or custom is needed |
| Cargo workspace layout | How to split kernel, plugins, and CLI into separate crates |

---

## 7. Strict Architectural Rule

> **The kernel calls plugins. Plugins never call the kernel.**

- Plugins receive events and act on them independently
- Plugins do NOT register new watches inside `on_event()`
- Plugins do NOT communicate with each other
- All new watch registrations happen in `setup()` only

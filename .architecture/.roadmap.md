# WatchEngine — Learning Roadmap

This roadmap builds the project from scratch in a specific order.
Each group has a clear concept to understand before writing any code.
Do not skip groups — each one is the foundation for the next.

---

## Group 1: Rust Foundations (No Code Yet)

Before touching the project, understand these Rust concepts.
They appear in every single group that follows.

- [ ] **Understand enums and pattern matching**
      Rust enums are not just named constants. They carry data.
      `FileEventKind` will be your first real enum.
      Resource: The Rust Book, Chapter 6.

- [ ] **Understand structs and impl blocks**
      How data and behavior are defined together in Rust.
      `FileEvent` and `Config` are structs.
      Resource: The Rust Book, Chapter 5.

- [ ] **Understand traits**
      A trait is a contract — a set of methods a type must implement.
      `WatchPlugin` is a trait. This is the most important concept in the project.
      Resource: The Rust Book, Chapter 10.

- [ ] **Understand trait objects (`Box<dyn Trait>`)**
      How Rust lets you hold different types behind a single interface at runtime.
      The Plugin Registry holds `Vec<Box<dyn WatchPlugin>>` — this is why.
      Resource: The Rust Book, Chapter 17 (Using Trait Objects).

- [ ] **Understand `Result<T, E>` and error handling**
      Rust has no exceptions. Errors are values.
      Every fallible function in this project returns `Result`.
      Resource: The Rust Book, Chapter 9.

- [ ] **Understand ownership and borrowing basics**
      Why Rust passes `&event` instead of `event`.
      You will encounter the borrow checker constantly.
      Resource: The Rust Book, Chapters 4 and 5.

- [ ] **Understand Rust modules and crate structure**
      How code is organized across files and crates.
      WatchEngine will have multiple crates in a workspace.
      Resource: The Rust Book, Chapter 7.

## Group 2: Workspace Setup

Learn how Cargo workspaces work, then set up the project structure.

- [ ] **Understand what a Cargo workspace is**
      A workspace is a collection of crates that share a single `Cargo.lock`.
      WatchEngine needs at least two crates: the kernel and the binary.
      Read: https://doc.rust-lang.org/book/ch14-03-cargo-workspaces.html

- [ ] **Create the workspace `Cargo.toml`**
      The root `Cargo.toml` lists all member crates.
      It has no `[package]` section — only `[workspace]`.

- [ ] **Create `watch-engine-core` crate**
      `cargo new --lib watch-engine-core`
      This is the kernel. It will have zero entries in `[dependencies]`.

- [ ] **Create `watch-engine` binary crate**
      `cargo new watch-engine`
      This is `main.rs` — the entry point. It depends on `watch-engine-core`.

- [ ] **Verify both crates compile**
      `cargo build` from the workspace root.
      Both crates should compile with no errors before any code is written.

## Group 3: Core Domain Types

These are the fundamental types the entire system is built on.
They live in `watch-engine-core` and have no external dependencies.

- [ ] **Understand why domain types live in the kernel**
      Every component — Reactor, Dispatcher, plugins — uses `FileEvent`.
      If it lives in the kernel, everyone can depend on the kernel to get it.

- [ ] **Define `FileEventKind` enum**
      Four variants: `Created`, `Modified`, `Deleted`, `Renamed { from: PathBuf }`.
      Practice: add `#[derive(Debug)]` and print one in a test.

- [ ] **Define `FileEvent` struct**
      Three fields: `path: PathBuf`, `kind: FileEventKind`, `timestamp: Instant`.
      Practice: construct one manually in a unit test.

- [ ] **Define `Config` struct**
      Three fields: `root: PathBuf`, `debounce_ms: u64`, `exec: Option<String>`.
      `exec` is `Option` because `--exec` is optional.

- [ ] **Define `WatchError` enum with `thiserror`**
      Add `thiserror` as the first (and only) dependency in `watch-engine-core`.
      Define at least: `WatchError::Io(#[from] std::io::Error)`.
      Learn: what `#[from]` does and why it's useful.

- [ ] **Write unit tests for all three types**
      Construct a `FileEvent`, a `Config`, and a `WatchError` in `#[cfg(test)]`.
      If they compile and print correctly, this group is done.

## Group 4: The Plugin Contract

The most important design step in the project.
Everything the kernel does flows through this trait.

- [ ] **Understand why the trait must be `Send + Sync`**
      The Dispatcher will call plugins from a different thread than where they were created.
      `Send` means: safe to move across threads.
      `Sync` means: safe to reference from multiple threads simultaneously.
      Read about `Send` and `Sync` in the Rust Book or Rustonomicon.

- [ ] **Define the `WatchPlugin` trait in `watch-engine-core`**

      ```rust
      pub trait WatchPlugin: Send + Sync {
          fn id(&self) -> &str;
          fn extensions(&self) -> &[&str];
          fn setup(&mut self, config: &Config) -> Result<Vec<PathBuf>, WatchError>;
          fn on_event(&self, event: &FileEvent);
      }
      ```

      Note: `setup()` now returns `Vec<PathBuf>` — the directories the plugin
      wants watched. The kernel registers them. Plugins never touch the watcher.

- [ ] **Write a fake plugin that implements the trait**
      Create a `struct FakePlugin` in a test module.
      Implement all four methods with minimal stubs.
      Goal: understand what it feels like to implement the trait before building the real plugins.

## Group 5: Plugin Registry

The kernel's memory — holds and manages all loaded plugins.

- [ ] **Understand `Vec<Box<dyn WatchPlugin>>`**
      Why `Box`? Because trait objects have no known size at compile time.
      Why `dyn`? Because the concrete type is not known — only the trait is.
      Practice: create a `Vec<Box<dyn WatchPlugin>>`, push two different fake plugins into it.

- [ ] **Implement `PluginRegistry` struct**
      One field: `plugins: Vec<Box<dyn WatchPlugin>>`.

- [ ] **Implement `register()` method**
      Takes a `Box<dyn WatchPlugin>` and pushes it into the vec.

- [ ] **Implement `find_by_extension()` method**
      Takes a `&str` extension (e.g. `".ts"`).
      Returns all plugins whose `extensions()` includes it or `"*"`.

- [ ] **Implement `setup_all()` method**
      Calls `plugin.setup(config)` on every registered plugin.
      Collects all returned `Vec<PathBuf>` into a single flat list.
      Returns that list to the caller (the kernel will watch those paths).

- [ ] **Write unit tests**
      Register two fake plugins, call `find_by_extension(".ts")`, assert correct plugins returned.
      Call `setup_all()`, assert all paths are returned.

---

## Group 6: Debouncer

Protects the kernel from being overwhelmed by rapid file events.

- [ ] **Understand the debounce concept**
      When a file is saved, the OS may fire 5-10 events in milliseconds.
      Debounce says: "only forward the event after things have settled for N ms."
      Draw it on paper: a timeline with events and the debounce window.

- [ ] **Understand `std::time::Instant` and `Duration`**
      `Instant::now()` captures the current moment.
      `instant.elapsed()` gives how much time has passed since then.
      Practice these two lines in isolation before using them.

- [ ] **Implement `Debouncer` struct**
      One field: `last_seen: HashMap<PathBuf, Instant>`.
      One config: `window: Duration`.

- [ ] **Implement `should_forward()` method**
      Takes a `&FileEvent`.
      Checks: has this path been seen within the last `window` duration?
      If yes: drop it (return `false`), update the timestamp.
      If no: forward it (return `true`), record the timestamp.

- [ ] **Write unit tests**
      Send the same path twice within the window — assert only the first passes.
      Send the same path after the window expires — assert it passes again.

---

## Group 7: Reactor

The kernel's event loop. The heart of the system.

- [ ] **Understand `std::sync::mpsc` channels**
      `mpsc` = multi-producer, single-consumer.
      `channel()` returns a `(Sender<T>, Receiver<T>)` pair.
      The Reactor owns the `Receiver`. The outside world gets the `Sender`.
      Practice: send a string through a channel in a small standalone program.

- [ ] **Implement `Reactor` struct**
      One field: `receiver: Receiver<FileEvent>`.
      Constructor takes the receiver: `Reactor::new(rx: Receiver<FileEvent>) -> Self`.

- [ ] **Implement `run()` method**
      Signature: `fn run(&mut self, debouncer: &mut Debouncer, dispatcher: &Dispatcher)`.
      Body: `loop { match self.receiver.recv() { Ok(event) => ..., Err(_) => break } }`.
      Inside the match: pass event to debouncer, if it passes, pass to dispatcher.

- [ ] **Write a unit test for the Reactor loop**
      Create a channel, send three `FileEvent`s through the sender, then drop the sender.
      Run the Reactor. Assert the dispatcher received the correct events.

---

## Group 8: Dispatcher

Routes a settled event to the right plugins and runs `--exec` if configured.

- [ ] **Implement `Dispatcher` struct**
      Two fields: `registry: &PluginRegistry`, `exec: Option<String>`.

- [ ] **Implement `dispatch()` method**
      Takes a `&FileEvent`.
      Calls `registry.find_by_extension(ext)`.
      Calls `plugin.on_event(event)` for each result.

- [ ] **Add `--exec` support using `std::process::Command`**
      If `self.exec` is `Some(cmd)`, run the command after plugin dispatch.
      Use `std::process::Command::new("sh").arg("-c").arg(cmd).spawn()`.
      Learn: what `.spawn()` does vs `.output()` — one is non-blocking, one blocks.

- [ ] **Write unit tests**
      Dispatch an event and assert the correct fake plugin's `on_event` was called.
      Dispatch an event with a mismatched extension — assert no plugin was called.

---

## Group 9: Kernel Integration Test

Before touching any external crate, verify the entire kernel works end-to-end.

- [ ] **Wire all kernel components together in a test**
      Create a channel, a Registry with two fake plugins, a Debouncer, a Dispatcher, a Reactor.
      Send a sequence of `FileEvent`s — some rapid (should be debounced), some spaced out.
      Run the Reactor for those events.

- [ ] **Assert the correct events reached the correct plugins**
      Rapid events for the same path → only one should reach the plugin.
      Events for `.ts` extension → only the TypeScript fake plugin should receive them.

- [ ] **This test has zero external dependencies**
      If it compiles and passes without `notify`, `tokio`, or `clap`, the kernel is correct.

## Group 10: notify Adapter

The bridge between the OS and the kernel. Lives outside the kernel.

- [ ] **Study the `notify` crate**
      Read the notify crate docs and examples.
      Understand `RecommendedWatcher`, `RecursiveMode`, and `notify::Event`.
      Understand what `notify::EventKind` variants exist.

- [ ] **Map `notify::EventKind` to `FileEventKind`**
      Write the translation table before writing code:
      `EventKind::Create(_)` → `FileEventKind::Created`
      `EventKind::Modify(_)` → `FileEventKind::Modified`
      etc.

- [ ] **Implement `NotifyAdapter` in `watch-engine` (not the core)**
      It takes a `Sender<FileEvent>` from the kernel.
      It creates a `RecommendedWatcher` that translates and sends events.

- [ ] **Implement `watch()` method**
      Registers a path with the underlying `notify` watcher.

- [ ] **Test manually**
      Create a temp directory, watch it, create a file, assert an event arrives in the channel.

---

## Group 11: CLI with clap

Parses user input and produces the `Config` and plugin list that drives the kernel.

- [ ] **Study `clap` derive macros**
      The derive approach lets you define CLI arguments as a struct with attributes.
      Read the clap derive documentation and run the basic example.

- [ ] **Define the `Cli` struct**
      Fields: `watch: PathBuf`, `typescript: bool`, `javascript: bool`,
      `debounce: u64`, `exec: Option<String>`.
      Derive `Parser` from clap.

- [ ] **Build `Config` from `Cli`**
      Write a `From<Cli>` implementation that maps CLI args to `Config`.

- [ ] **Register plugins based on flags**
      If `cli.typescript` is true, register `TypeScriptPlugin`.
      If `cli.javascript` is true, register `JavaScriptPlugin`.
      Always register `GenericPlugin` as fallback.

- [ ] **Test the CLI parsing**
      Parse a hardcoded args string, assert the correct `Config` fields are set.

---

## Group 12: GenericPlugin

The first real plugin. The simplest one — no file-type discovery needed.

- [ ] **Create `GenericPlugin` struct**
      No fields needed initially.

- [ ] **Implement `setup()`**
      Returns `vec![config.root.clone()]` — watches the root recursively.
      No walkdir needed. The kernel handles recursive watching via notify.

- [ ] **Implement `on_event()`**
      Print the event to stdout:
      `println!("[{:?}] {}", event.kind, event.path.display())`.

- [ ] **Register it in `main.rs` and run end-to-end**
      Create a temp directory, run the engine, create a file, see the output.
      This is your first working version of WatchEngine.

---

## Group 13: TypeScriptPlugin

The first plugin that does real file-type discovery.

- [ ] **Study the `walkdir` crate**
      `WalkDir::new(path)` recursively walks a directory tree.
      Read the docs and write a small standalone program that prints all `.ts` files.

- [ ] **Implement `setup()`**
      Use `walkdir` to find every directory under `config.root` that contains
      at least one `.ts` or `.tsx` file.
      Return that list of directories.

- [ ] **Implement `on_event()`**
      Same as GenericPlugin — print the event to stdout.
      Optionally prefix with `[typescript]` to distinguish output.

- [ ] **Test with a real directory structure**
      Create a temp directory with nested folders containing `.ts` files.
      Run the engine with `--typescript`, modify a file, see the output.

---

## Group 14: JavaScriptPlugin

Same pattern as TypeScript. Good consolidation of what you learned.

- [ ] **Implement `setup()` for `.js`, `.mjs`, `.cjs`**
- [ ] **Implement `on_event()`**
- [ ] **Test end-to-end**

## Group 15: Full Integration

Wire everything together and validate the complete system.

- [ ] **Write `main.rs`**
      Parse CLI → build Config → create channel → create NotifyAdapter →
      register plugins → run setup_all → watch returned paths → start Reactor loop.

- [ ] **End-to-end test: TypeScript file change**
      Run `watch-engine --typescript --watch ./some-ts-project`.
      Modify a `.ts` file. Assert correct output.

- [ ] **End-to-end test: `--exec` flag**
      Run with `--exec "echo file changed"`.
      Modify a file. Assert the command runs.

- [ ] **End-to-end test: debounce**
      Save a file rapidly multiple times.
      Assert the output shows far fewer events than saves.

- [ ] **Test on Linux or Windows (if available)**
      The notify adapter should work transparently.
      The kernel tests will pass unchanged — they have no OS dependency.

## Reference: Crate Dependency Map

```
watch-engine-core   (kernel)
  └── [dependencies]: thiserror only

watch-engine        (binary)
  └── [dependencies]: watch-engine-core, notify, clap, walkdir, tracing, tracing-subscriber
```

The kernel crate never gains new dependencies.
All external crates live in the binary crate.

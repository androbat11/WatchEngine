# Notify Adapter

## What It Is

The Notify Adapter is the bridge between the operating system and the kernel.
It lives outside the kernel in the `watch-engine` binary crate.

Its job is simple:

1. Wrap the `notify` crate's OS-specific watcher
2. Translate raw `notify::Event` into the kernel's `FileEvent`
3. Send each translated event into the kernel's channel

The kernel never sees `notify`. The Notify Adapter is the only place in the
entire codebase that imports it.

---

## Where It Sits

```text
Operating System
  │  (FSEvents / inotify / ReadDirectoryChangesW)
  ▼
notify crate  (cross-platform abstraction)
  │  notify::Event { kind, paths, ... }
  ▼
Notify Adapter  ◄── you are here
  │  translates to FileEvent
  │  sends through Sender<FileEvent>
  ▼
Reactor (kernel)
  │  receives via Receiver<FileEvent>
  ▼
rest of kernel...
```

---

## The Channel Bridge

The kernel creates the channel and keeps the `Receiver` end inside the Reactor.
The Notify Adapter receives the `Sender` end and writes into it.

```text
main.rs:
  let (tx, rx) = std::sync::mpsc::channel::<FileEvent>();
  let adapter  = NotifyAdapter::new(tx);   ← gets the sender
  let reactor  = Reactor::new(rx);         ← gets the receiver
```

This means the kernel does not depend on `notify` at all.
The kernel only depends on receiving `FileEvent`s through a channel.
The source of those events is irrelevant to it.

## Event Translation

`notify::EventKind` has many variants. Most map cleanly to `FileEventKind`.

```text
notify::EventKind::Create(_)                  →  FileEventKind::Created
notify::EventKind::Modify(ModifyKind::Data(_)) →  FileEventKind::Modified
notify::EventKind::Remove(_)                  →  FileEventKind::Deleted
notify::EventKind::Modify(ModifyKind::Name(_)) →  FileEventKind::Renamed { from }
notify::EventKind::Access(_)                  →  ignored (read-only, not a change)
notify::EventKind::Other                      →  ignored
```

The `Renamed` case is the hardest. On Linux (`inotify`), a rename fires two
events: `IN_MOVED_FROM` and `IN_MOVED_TO`, linked by a cookie integer.
The Notify Adapter must hold the first event until the second arrives, then
emit one `FileEventKind::Renamed { from: old_path }` with the new path.

On Windows, the same pairing problem exists with `FILE_ACTION_RENAMED_OLD_NAME`
and `FILE_ACTION_RENAMED_NEW_NAME`. The `notify` crate handles some of this
internally — check the `notify` docs for the current behavior per platform.

## What `RecommendedWatcher` Is

`notify::RecommendedWatcher` is a type alias that resolves at compile time to
the correct backend for the target OS:

```text
macOS   →  FsEventWatcher    (wraps FSEvents C API)
Linux   →  INotifyWatcher    (wraps inotify syscalls)
Windows →  ReadDirectoryChangesWatcher
```

You write one call: `RecommendedWatcher::new(callback, config)`.
The OS-specific code is selected by the compiler. You never branch on OS.

---

## The `watch()` Method

After construction, the adapter exposes a `watch()` method the kernel calls
with the list of paths returned by `Registry.setup_all()`:

```text
for path in registry.setup_all(&config) {
    adapter.watch(&path, recursive)?;
}
```

`RecursiveMode::Recursive` tells `notify` to watch the entire subtree.
On Linux, `notify` handles the per-subdirectory `inotify_add_watch` calls
internally so you do not have to iterate subdirectories yourself.

## Rust Concepts Involved

**Closures as callbacks**
`notify::RecommendedWatcher::new` takes a closure that is called for each event.
Inside the closure you translate and send: `tx.send(file_event)`.
The closure captures `tx` by value (move closure).
Read: The Rust Book, Chapter 13.1 — <https://doc.rust-lang.org/book/ch13-01-closures.html>

**Move closures**
The `tx` (Sender) must be moved into the closure because the closure runs
on the notify background thread — not on the thread that created `tx`.
`move || { tx.send(...) }` transfers ownership of `tx` into the closure.
Read: The Rust Book, Chapter 16.1 — <https://doc.rust-lang.org/book/ch16-01-threads.html>

**`notify` crate API**
`notify::RecommendedWatcher`, `RecursiveMode`, `EventKind`, `ModifyKind`.
Read: <https://docs.rs/notify/latest/notify/>

## Recommended Reading

### How the OS Layer Works

**`notify` crate internals — source and changelog**
Reading the notify source code shows exactly how each OS backend is implemented.
The `src/inotify.rs`, `src/fsevent.rs`, and `src/windows.rs` files are
illuminating.
<https://github.com/notify-rs/notify>

**inotify — Linux kernel documentation**
The canonical explanation of how inotify works at the syscall level:
`inotify_init`, `inotify_add_watch`, `read()` on the fd, the event struct.
<https://man7.org/linux/man-pages/man7/inotify.7.html>

**FSEvents — Apple developer documentation**
Apple's official documentation for the FSEvents framework, including the
CFRunLoop delivery model, coalescing behavior, and historical replay.
Search: "Apple FSEvents Programming Guide"

**Adapter Pattern (Gang of Four)**
The Notify Adapter is a textbook Adapter pattern — it converts the interface
of `notify` (which the kernel cannot use directly) into the interface the
kernel expects (`Sender<FileEvent>`). Reading the GoF chapter on Adapter
gives you the vocabulary to describe what this component does.
Read: GoF "Design Patterns" — Adapter chapter.
Search: "Adapter pattern explained structural patterns"

**Cross-platform abstraction strategies**
The `notify` crate uses Rust's `#[cfg(target_os)]` conditional compilation to
select the right backend. Understanding how conditional compilation works in
Rust explains how one `RecommendedWatcher` type works on all three OSes.
Read: The Rust Reference — Conditional Compilation
<https://doc.rust-lang.org/reference/conditional-compilation.html>

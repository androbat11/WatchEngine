# CLI (Command Line Interface)

## What It Is

The CLI is the entry point of WatchEngine. It runs once at startup,
parses the user's flags, builds a `Config`, registers plugins, and then
hands everything to the kernel and steps aside.

It is not part of the kernel. It is a startup driver.

---

## What It Does (Sequence)

```text
1. User runs:  watch-engine --typescript --watch ./project --exec "echo changed"

2. clap parses the arguments into a Cli struct

3. CLI builds Config from the struct:
     Config { root: "./project", debounce_ms: 300, exec: Some("echo changed") }

4. CLI creates the channel:
     let (tx, rx) = std::sync::mpsc::channel::<FileEvent>()

5. CLI creates the NotifyAdapter with the sender:
     let adapter = NotifyAdapter::new(tx)

6. CLI creates the Reactor with the receiver:
     let reactor = Reactor::new(rx)

7. CLI creates the PluginRegistry and registers plugins:
     registry.register(Box::new(TypeScriptPlugin::new()))  ← because --typescript
     registry.register(Box::new(GenericPlugin::new()))     ← always registered

8. CLI calls setup_all — plugins discover directories:
     let paths = registry.setup_all(&config)?

9. CLI registers each path with the adapter:
     for path in paths { adapter.watch(&path)? }

10. CLI starts the kernel:
     reactor.run(&mut debouncer, &mut dispatcher)
     ← this blocks forever until Ctrl+C
```

After step 10, the CLI is done. The kernel runs for the rest of the process lifetime.

## The `Cli` Struct

```rust
#[derive(clap::Parser)]
#[command(name = "watch-engine", about = "Lightweight file watcher")]
pub struct Cli {
    /// Directory to watch
    pub watch: PathBuf,

    /// Watch TypeScript files (.ts, .tsx)
    #[arg(long)]
    pub typescript: bool,

    /// Watch JavaScript files (.js, .mjs, .cjs)
    #[arg(long)]
    pub javascript: bool,

    /// Debounce window in milliseconds
    #[arg(long, default_value = "300")]
    pub debounce: u64,

    /// Shell command to run after each change
    #[arg(long)]
    pub exec: Option<String>,
}
```

`#[derive(clap::Parser)]` generates all the parsing logic from the struct fields.
No manual argument parsing needed.

## Building `Config` from `Cli`

```rust
impl From<Cli> for Config {
    fn from(cli: Cli) -> Self {
        Config {
            root:        cli.watch,
            debounce_ms: cli.debounce,
            exec:        cli.exec,
        }
    }
}
```

`From<T>` is a standard Rust conversion trait. Implementing it here means
you can write `Config::from(cli)` or `cli.into()` anywhere in main.

---

## Plugin Registration

The CLI is the only place that knows which concrete plugins exist.
It decides which to register based on the flags:

```text
--typescript  →  register TypeScriptPlugin
--javascript  →  register JavaScriptPlugin
(always)      →  register GenericPlugin (fallback)
```

After main returns from this registration step, the kernel only sees
`Box<dyn WatchPlugin>` — it has no idea TypeScriptPlugin exists.

## Rust Concepts Involved

**`clap` derive macros**
The `#[derive(clap::Parser)]` macro reads your struct at compile time and
generates a full argument parser. Each field becomes a CLI argument.
The `#[arg(...)]` attribute customizes behavior per field.
Read: <https://docs.rs/clap/latest/clap/_derive/_tutorial/index.html>

**`From` and `Into` traits**
`From<T>` and `Into<T>` are reciprocal. Implementing `From<Cli> for Config`
automatically gives you `Into<Config> for Cli` for free.
These are the idiomatic Rust conversion traits.
Read: <https://doc.rust-lang.org/std/convert/trait.From.html>

**`PathBuf` from a string argument**
clap automatically converts a string argument into a `PathBuf` when the field
type is `PathBuf`. No manual conversion needed.

### The Composition Root Pattern

**Composition Root — Mark Seemann**
The CLI's role in WatchEngine is the Composition Root — the single place in
the application where all components are assembled and wired together.
Mark Seemann's concept explains why this wiring must happen in one place
(here: `main.rs`) and not be scattered across the codebase.
Search: "Composition Root pattern Mark Seemann"

**Pure DI (Dependency Injection without a framework)**
WatchEngine does pure DI: the CLI manually constructs plugins and passes them
to the registry. No DI container or framework is needed. Understanding why
this is often preferable to a framework-based approach helps you see the
simplicity of the current design.
Search: "Pure DI vs DI container Mark Seemann"

# TypeScriptPlugin

## What It Is

The TypeScriptPlugin watches `.ts` and `.tsx` files.
It does not run `tsc`. It does not typecheck anything.
It watches — and when a TypeScript file changes, it reports it.

WatchEngine exists to replace the heavy file-watching overhead of `tsc --watch`.
This plugin is the lightweight alternative: directory discovery + event emission.
No compiler process, no language server, no memory spike.

---

## What Makes It Different From GenericPlugin

GenericPlugin watches everything from the root.
TypeScriptPlugin watches only directories that contain TypeScript files.

This distinction matters for large projects. If your project has 200
subdirectories but TypeScript files only exist in 12 of them, the plugin
registers 12 watches instead of 200. Fewer OS watches = less kernel overhead.

---

## `setup()` — Directory Discovery

This is the plugin's main contribution. It walks the entire directory tree
and returns only the folders that contain at least one `.ts` or `.tsx` file.

```text
Project tree:
  /project/
    src/
      components/     ← has Button.tsx    → WATCH
      utils/          ← has helpers.ts    → WATCH
      styles/         ← only .css files   → skip
    tests/
      unit/           ← has foo.test.ts   → WATCH
      fixtures/       ← only .json files  → skip
    docs/             ← only .md files    → skip

setup() returns: [/project/src/components, /project/src/utils, /project/tests/unit]
```

The kernel registers exactly those three directories with the OS watcher.
No watches on `styles/`, `fixtures/`, or `docs/`.

## `on_event()` — Reporting

```rust
fn on_event(&self, event: &FileEvent) {
    println!("[typescript] {:?} → {}", event.kind, event.path.display());
}
```

That is the entire implementation. One line. The heavy lifting was in `setup()`.

## Implementation Sketch

```rust
pub struct TypeScriptPlugin;

impl WatchPlugin for TypeScriptPlugin {
    fn id(&self) -> &str { "typescript" }

    fn extensions(&self) -> &[&str] { &[".ts", ".tsx"] }

    fn setup(&mut self, config: &Config) -> Result<Vec<PathBuf>, WatchError> {
        let mut dirs = std::collections::HashSet::new();

        for entry in walkdir::WalkDir::new(&config.root) {
            let entry = entry?;
            let path  = entry.path();

            if is_ts_file(path) {
                if let Some(parent) = path.parent() {
                    dirs.insert(parent.to_path_buf());
                }
            }
        }

        Ok(dirs.into_iter().collect())
    }

    fn on_event(&self, event: &FileEvent) {
        println!("[typescript] {:?} → {}", event.kind, event.path.display());
    }
}

fn is_ts_file(path: &Path) -> bool {
    matches!(
        path.extension().and_then(|e| e.to_str()),
        Some("ts") | Some("tsx")
    )
}
```

A `HashSet` is used to deduplicate directories — multiple `.ts` files in the
same folder should only register one watch for that folder.

## Rust Concepts Involved

**`walkdir` crate**
`WalkDir::new(path)` returns an iterator over every file and directory in the tree.
Each item is a `walkdir::DirEntry` with methods like `.path()` and `.file_type()`.
Read: <https://docs.rs/walkdir/latest/walkdir/>

**`HashSet<T>` for deduplication**
A `HashSet` stores unique values. Using it to collect parent directories
automatically deduplicates: even if 10 `.ts` files are in the same folder,
that folder only appears once in the set.
Read: <https://doc.rust-lang.org/std/collections/struct.HashSet.html>

**`matches!` macro**
`matches!(expr, pattern1 | pattern2)` returns `true` if the expression matches
any of the patterns. Cleaner than a `match` block when you only care about
true/false.
Read: <https://doc.rust-lang.org/std/macro.matches.html>

**`Path::extension()` and `OsStr`**
File extensions in Rust come back as `Option<&OsStr>`. The `.to_str()` call
converts to `Option<&str>`. Both can be `None` for files without extensions.
Read: <https://doc.rust-lang.org/std/path/struct.Path.html#method.extension>

## Recommended Reading

**`walkdir` crate documentation**
The full API including how to filter entries, follow symlinks, set max depth.
<https://docs.rs/walkdir/latest/walkdir/>

**File system traversal algorithms**
`walkdir` implements depth-first traversal. Understanding the difference
between depth-first and breadth-first traversal explains why some directories
are visited before others, which matters if you are debugging discovery order.
Search: "depth-first vs breadth-first file system traversal"

**Why `tsc --watch` is slow — the actual reason**
Understanding what TypeScript's built-in watcher does (persistent process,
language service, incremental compilation, type graph in memory) makes the
design of WatchEngine's TypeScriptPlugin make more sense. WatchEngine does
none of that — it only watches.
Search: "TypeScript watch mode memory usage" or "tsc --watch performance"

**Inode watching vs directory watching**
On Linux, inotify watches inodes. On macOS, FSEvents watches directory trees.
A plugin that discovers directories (like this one) maps well to both models:
directories are the unit of registration on both platforms.
Search: "inotify vs FSEvents directory watching comparison"

# JavaScriptPlugin

## What It Is

The JavaScriptPlugin watches `.js`, `.mjs`, and `.cjs` files.
Same design as `TypeScriptPlugin` — directory discovery in `setup()`,
event emission in `on_event()`. No Node.js process, no bundler, no runtime.

---

## Extensions

```text
.js   — standard JavaScript module
.mjs  — explicit ES module (ECMAScript module)
.cjs  — explicit CommonJS module
```

All three are registered because modern JavaScript projects use a mix.
A project using ES modules will have `.mjs` files. A project using CommonJS
will have `.cjs` files. A legacy project uses `.js` for both.

---

## `setup()` — Directory Discovery

Identical strategy to TypeScriptPlugin: walk the tree, collect parent
directories of matching files, deduplicate with a `HashSet`.

```text
Project tree:
  /project/
    src/
      index.js        → WATCH /project/src
      utils.mjs       → WATCH /project/src  (already in set, deduped)
    scripts/
      build.cjs       → WATCH /project/scripts
    tests/
      spec.js         → WATCH /project/tests
    styles/           ← no .js files → skip

setup() returns: [/project/src, /project/scripts, /project/tests]
```

## `on_event()` — Reporting

```rust
fn on_event(&self, event: &FileEvent) {
    println!("[javascript] {:?} → {}", event.kind, event.path.display());
}
```

## Overlap With TypeScriptPlugin

A TypeScript project often contains both `.ts` and `.js` files.
If both `--typescript` and `--javascript` are active, both plugins will call
`on_event()` for a `.ts` file — wait, no. Only TypeScriptPlugin handles `.ts`.
Only JavaScriptPlugin handles `.js`.

But both plugins' discovered directories may overlap. If `/project/src`
contains both `.ts` and `.js` files, both plugins return it from `setup()`.
The kernel deduplicates watch registrations before calling `notify` — watching
the same directory twice would produce duplicate events.

This deduplication happens in `main.rs` before calling `adapter.watch()`:

```rust
let paths: std::collections::HashSet<PathBuf> = registry
    .setup_all(&config)?
    .into_iter()
    .collect();

for path in paths {
    adapter.watch(&path)?;
}
```

## Rust Concepts Involved

Same concepts as TypeScriptPlugin:
`walkdir`, `HashSet`, `Path::extension()`, `matches!` macro.

One addition specific to this plugin:

**Multiple extension matching**
TypeScript had two extensions. JavaScript has three. The `is_js_file` helper
uses the same `matches!` pattern:

```rust
fn is_js_file(path: &Path) -> bool {
    matches!(
        path.extension().and_then(|e| e.to_str()),
        Some("js") | Some("mjs") | Some("cjs")
    )
}
```

## Recommended Reading

**ES Modules vs CommonJS — the history**
Understanding why `.mjs` and `.cjs` exist (the Node.js module system split)
explains why the plugin needs to watch all three extensions.
Search: "ES modules vs CommonJS Node.js history" or "mjs cjs difference"

**Why watch only directories, not individual files**
Registering a watch per directory (not per file) is more efficient because
new files added to a watched directory are automatically covered. If you
watched individual files, a newly created `newfile.js` in a watched directory
would be invisible until you added a new watch for it.
Search: "inotify directory watch vs file watch"

**Code reuse between TypeScript and JavaScript plugins**
Both plugins share nearly identical `setup()` logic. In a real codebase you
would extract the common "walk and collect parent directories" logic into a
shared helper function. This is the Don't Repeat Yourself (DRY) principle in
practice — but only extract when there is genuine duplication, not anticipatory.
Search: "DRY principle when to apply"

# GenericPlugin

## What It Is

The GenericPlugin is the fallback — it matches every file that no other plugin
claimed. It is always registered, regardless of what flags the user passes.

It is also the simplest plugin to implement. It does no directory discovery,
has no file-type filtering, and its `on_event()` does exactly one thing:
print the event to stdout.

Start here when learning how to implement the `WatchPlugin` trait.

---

## Role in the System

```text
User changes /project/README.md

Dispatcher asks Registry: who handles ".md"?
  → TypeScriptPlugin: no (.md not in [".ts", ".tsx"])
  → JavaScriptPlugin: no (.md not in [".js", ...])
  → GenericPlugin:    YES ("*" matches everything)

GenericPlugin.on_event() called
Output: [CHANGE] Modified → /project/README.md
```

The `"*"` wildcard ensures no file change goes unnoticed.
Even if the user only passes `--typescript`, changing a `.json` or `.md` file
will still produce output — from the GenericPlugin.

## Implementation

```rust
pub struct GenericPlugin;

impl WatchPlugin for GenericPlugin {
    fn id(&self) -> &str {
        "generic"
    }

    fn extensions(&self) -> &[&str] {
        &["*"]
    }

    fn setup(&mut self, config: &Config) -> Result<Vec<PathBuf>, WatchError> {
        Ok(vec![config.root.clone()])
    }

    fn on_event(&self, event: &FileEvent) {
        println!("[CHANGE] {:?} → {}", event.kind, event.path.display());
    }
}
```

`setup()` returns a single path — the root directory. The kernel's `notify`
adapter watches it recursively. No `walkdir` needed.

---

## Why No File Discovery Needed

TypeScript and JavaScript plugins walk the directory tree to find only folders
containing their file type. The Generic plugin skips this because it watches
everything — there is no filter to apply. Watching the root recursively covers
all files in the project.

## Rust Concepts Involved

**Unit struct**
`struct GenericPlugin;` is a unit struct — a struct with no fields.
It takes zero bytes of memory. It exists purely as a named type to implement
the trait on.
Read: The Rust Book, Chapter 5.1 — <https://doc.rust-lang.org/book/ch05-01-defining-structs.html>

**`PathBuf::clone()`**
`config.root.clone()` creates an owned copy of the path.
`setup()` returns `Vec<PathBuf>` (owned), so we cannot return a reference to
`config.root` — the reference would outlive `config`. Clone gives us ownership.

**`Path::display()`**
`path.display()` returns a type that implements `Display`, suitable for
`println!`. It handles non-UTF-8 paths gracefully.
Read: <https://doc.rust-lang.org/std/path/struct.Path.html#method.display>

## Recommended Reading

**Null Object Pattern (Gang of Four)**
The GenericPlugin is an application of the Null Object pattern — instead of
having no fallback (which would require null checks everywhere), you provide a
default implementation that does something harmless. The Dispatcher never needs
to check "did any plugin match?" — the Generic always does.
Search: "Null Object pattern explained"

**Fallback and default behavior in plugin systems**
Most plugin systems have a concept of a default or fallback handler.
Reading how vim's default keybindings work, or how Express.js middleware
fallthrough works, gives practical intuition for why this pattern is needed.
Search: "Express.js middleware next() fallthrough" or "vim default keymap"
